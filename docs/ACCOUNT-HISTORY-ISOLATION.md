# 账号与个人历史改造

此分支基于上游 v0.8.1，尚未部署到现有服务器

## 身份与权限

- 使用 App Hub 自己的邮箱密码账号，不要求创建 Dify 管理账号
- 初始化创建管理员，管理员可创建普通账号、分配角色、停用、启用和修改密码
- 普通用户进入 /apps 与 /chat，后台页面、管理 API 和 Server Actions 要求管理员角色
- 当前所有启用账号共享可用助手列表，尚无逐应用授权配置
- users.dify_user_id 为持久身份，修改姓名、邮箱、密码或启停不会重新生成
- 所有 /api/client 路由直接检查真实会话，并覆盖 query、JSON、FormData 中的 user，客户端 x-user-id 不作为凭据
- 聊天正文保留在 Dify，历史列表与续问仍使用现有 API
- 改密、启停与角色修改递增 session_version，下一个 API 请求即拒绝旧会话；已经开始的流式回答不会追溯撤销
- 浏览器每 30 秒及重新聚焦时检查会话，退出采用完整导航，避免保留旧账号页面状态
- 不提供公开注册，登录页提示联系管理员处理密码

## 数据库迁移

在独立测试库评审并运行新增迁移前，不得启动此分支连接已有业务库

迁移需为历史账号回填 hub_ + 原账号 ID，并将最早创建的历史账号保留为管理员；新建空库通过初始化页面创建管理员

新增 user_files 记录上传文件归属，防止仅凭 fileId 预览他人文件

## MySQL 5.7 测试环境

用户提供的测试地址为 10.2.96.232:3306，版本为 MySQL 5.7，尚未提供凭据或连接数据库

- 创建独立的 dify_app_hub_test 库，建议字符集 utf8mb4、排序规则 utf8mb4_unicode_ci
- 先核对准确版本、innodb_default_row_format 与 innodb_large_prefix，email 的 utf8mb4 唯一索引需大前缀索引支持
- 三个上游历史 SQL 文件仅将 DEFAULT (CURRENT_TIMESTAMP(3)) 规范为 5.7 支持的 DEFAULT CURRENT_TIMESTAMP(3)，不改变字段业务含义
- 本分支用于新测试库；不要用修改后的历史文件盲目恢复已有生产数据库或手工调整迁移日志
- 后续新增迁移同样需要检查 MySQL 5.7 语法；自动生成 SQL 不代表已经兼容目标数据库

参考：https://docs.oracle.com/cd/E17952_01/mysql-5.7-en/timestamp-initialization.html

## 现有 Python 门户历史

本分支默认产生新的 hub_ 身份，不自动合并旧分享页或 Python 门户历史

若需延续 Python 门户历史，必须先备份，并核验 username 与真实同事账号的一一对应关系，再由管理员在离线迁移中导入 dify_identities.user_id 到 users.dify_user_id

不开放普通用户修改此字段，也不能凭一条日志中的字符串认领历史；需要保持同一个 Dify 应用和 API 身份渠道

## 附件及浏览器缓存边界

- 上传请求仍由现有 Dify 处理，门户追加记录文件所属身份
- 文件预览仅开放本门户记录的本人上传文件；旧文件或模型生成文件尚未登记归属时返回 404，不按猜测放行
- 文档解析、OCR 与图片理解仍依赖 Dify Chatflow 节点及模型
- 工作流详情和思考时长缓存按 App Hub 账号 ID 分开保存，账号缓存加载完成后才挂载聊天；旧匿名缓存不读取或删除，会话正文由 Dify 恢复
- Dify 返回的签名文件 URL、防火墙暴露入口及反向代理部署仍需单独验收
